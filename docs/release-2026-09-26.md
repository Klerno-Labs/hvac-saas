## Pre-existing service blockers

- Before any release, production `/api/health` returned HTTP 503 with a failed database check. Both A and AAAA lookups for the configured Supabase database host returned ENOTFOUND. The project is not listed in the authenticated Supabase account's four organizations. The existing database must be located/restored before backup, migration rehearsal, migration or promotion. No production database has been replaced, seeded or migrated.
- Stripe is configured in **test mode**. The existing price IDs resolve to active USD 49/month Starter and USD 99/month Pro prices. No webhook endpoint with a FieldClose URL was registered. Live payments require the correct live account, matching prices, separately signed platform/Connect endpoints and verified deliveries.
- R2 photo storage, Twilio SMS and OpenAI are not configured in the current production project. Email delivery has not been exercised against a real recipient during this release.

## Hosting fixes

Removed accidental trailing newlines from the existing database, email, Stripe key/price and scheduler settings. Kept `AUTH_SECRET` unchanged. Added `CRON_SECRET` using the existing scheduler token, so Vercel can authenticate its requests. These changes apply to a subsequent deployment; they do not repair the missing database.

Scheduled endpoints now accept authenticated GET requests and retain authenticated POST support. Daily schedules fit the current Vercel Hobby configuration. `SCHEDULED_TASKS_ENABLED=false` is set for the next deployment so staged production builds cannot run operational work before database recovery and migration. Change it to `true` and build the final release only after those checks pass. The deployment source explicitly excludes local credentials, dependency folders and build artifacts.

## Promotion gate

Build a production candidate with `vercel deploy --prod --skip-domain` from the repository root, using the existing linked project. Do not promote it or merge a branch that automatically deploys to production until the database is verified.

After database access is restored: capture a recoverable backup and schema/migration history; rehearse the exact migration path on an isolated copy; reconcile already-applied schema changes rather than blindly executing or resolving `0005`; apply required migrations; verify schema parity and protected workflows; then promote the candidate and run live smoke checks. A successful build or `SELECT 1` alone is not sufficient.

Old sessions require a fresh sign-in after this release because of credential-version validation. Do not create synthetic accounts or send customer messages in production as part of an unapproved smoke test.
